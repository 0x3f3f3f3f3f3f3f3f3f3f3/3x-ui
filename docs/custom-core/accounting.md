# Identity, metering and enforcement contract

Status: runtime primitives, Tunnel admission, local durable reservations and transactional panel ledger primitives are implemented and tested. Production runtime activation, rollback fencing and multi-node budgets remain unfinished. Full intended semantics remain below.

- `client_id` is a panel-generated opaque UUID, independent of display email, protocol UUID/password/PSK, port and node. Migration assigns once and preserves old email-keyed API/statistics compatibility. Deletion/recreation gets a new identity; shared subscriptions alone are not sufficient identity evidence.
- Count decoded TCP bytes and complete UDP payloads at the admission boundary, once per business leg. Separately label IP-packet paths. A byte admitted toward a destination counts even if the remote subsequently fails; kernel retransmissions, encrypted frames, sniff replay and internal bridge copies do not count again.
- Raw upload/download and billed total are separate. Fixed point uses multiplier millionths, positive range 0.000001–1000.000000; no float input accumulation. Preserve sub-byte millionths over batches and multiplier changes. Detect arithmetic overflow before mutation. Legacy multiplier is 1 and old billed usage equals old raw usage without resetting it.
- A policy version creates an exact admission boundary: prior usage keeps the old multiplier; subsequent bytes use the new one. Lowering quota below charged use restricts immediately.
- Per-client upload/download rates are bytes/second, independently configured; zero means unlimited. UI must label Mbps conversion distinctly. Shared token buckets have explicit bounded burst. For interval T admitted bytes must be ≤ R*T+B plus documented clock granularity; old-policy admitted buffers are separately reported at updates. UDP datagrams stay intact; wait in a bounded queue or reject/drop with an explicit counter.
- Disabled, expired, quota exhausted, unavailable budget and revoked identity are independent restriction reasons. Reset/top-up/renewal only clears the applicable reason. Apply changes to existing sessions, including idle sessions and UDP/reverse listeners.
- Normal quota admission uses one atomic check/debit across both directions and all connections. Do not call periodic panel polling an enforcement mechanism. Track admitted-but-not-written bytes separately when reporting endpoint observations.

## Durability design

Panel issues versioned budgets; core durably reserves bounded portions before admitting payload. Committed raw/billed counters and event cursor are saved together, events carry core instance, epoch, sequence and policy version. On uncertain crash recovery an outstanding reservation remains spent/unavailable until reconciled, never freely reissued. Do not fabricate raw traffic for an uncertain reservation: report conservative reserved usage separately. A persistence failure closes/rejects managed sessions.

Before implementation acceptance, choose and test the exact reservation quantum, maximum outstanding reservations, crash uncertainty and overshoot bound. No claim of zero overuse is made here. Local file loss or rollback is not equivalent to a fresh account; require panel reconciliation/fencing. Restoring a panel backup must not overlap live node budgets. DB transactions atomically commit totals plus idempotency cursor; multiplier applies once in the core event, not again at node aggregation.

## Tests fixed before runtime implementation

Multipliers: 0.5, 1, 1.5, 2, 10; arbitrary split batches must produce identical totals/remainders. 10 GiB at 1 then 5 GiB at 2 bills 20 GiB. A 100 MiB quota at 2 permits at most 50 MiB admitted bidirectional raw bytes (whole datagram granularity may leave budget unused). Concurrency test contends on the final budget. Compare independent sender/receiver observations at the same boundary; echoes count both directions.

Rate measurements: 256 KiB/s and 1 MiB/s, burst 64 KiB, 10-second steady windows after a 2-second warmup; unlimited baseline must exceed 4 MiB/s or result is inconclusive. Upper bound R*T+B+1% timing allowance; healthy steady throughput at least 85% of R. Report scheduling/buffer uncertainty, startup burst and update delay separately. These are initial gates, not numbers to loosen after failures.

## Current execution boundary and limitation

Dispatcher wraps the routed decoded payload after sniff caching. Upload admission occurs before handing buffers to the outbound; download admission occurs before writing each buffer to the client. Quota exhaustion cancels every registered session, including idle connections. This can discard the final admitted in-flight buffers: the 100 MiB/2× echo test observed 8192 bytes admitted but not delivered to the receiving application. No claim of delivered-byte-perfect accounting is made. The admitted budget was not exceeded. Configured core traffic now uses durable reservations; the whole task 4 contract is not complete and installation/upgrade integration remains pending.

## Implemented local reservation protocol

The execution store uses MIT-licensed bbolt v1.5.0 with synchronous transactions, an exclusive process lock, private file permissions and a 256 MiB file bound. The state holds panel-issued policies, exact checkpointed directional counters/fraction, persistent revocation tombstones, frozen uncertain bytes, reservation ceiling and a monotonically committed sequence. A stable store instance ID is checked on open; each successful open atomically increments its epoch. Missing state is an error; initialization is a separate explicit action, never an automatic response to missing/corrupt data.

Per client, at most one 65,536-raw-byte reservation is outstanding across upload and download combined. Its billable ceiling is committed before any bytes in that block are admitted. Near quota, the reserved raw amount is reduced to the affordable whole-byte budget. Payload admission may not exceed that quantum. A reservation refill checkpoints exact prior usage, then reserves the next block in the same transaction. A policy/multiplier update atomically checkpoints prior usage and releases unused reservation before applying the new version. Batch updates validate every member before one database transaction. Permanent client-ID tombstones prevent reuse after restart.

On clean checkpoint/shutdown the exact admitted counters are committed and unused reservation released. On abrupt restart, the prior outstanding billable ceiling becomes frozen `uncertainBytes`; checkpointed raw counters remain unchanged. The ceiling rounds upward by less than one billed byte, independently reported from confirmed billing. Maximum additional unavailable budget per client per abrupt exit is `ceil(65536 × multiplier + prior fractional remainder)` billed bytes, capped by the last reservation's affordable amount. At multiplier 2 this is at most 131,072 bytes when prior remainder is zero. Repeated restart without new admission creates no new reservation. Full/ambiguous I/O failure closes all managed sessions and blocks further policy/data admission; recovery keeps possibly committed reservations frozen.

This bounds **unavailable budget**, not confirmed delivered traffic. Committed reservations prevent reissuing admitted quota after the tested process crashes, assuming the store and its filesystem durability contract remain intact. File loss, administrator rollback, cloned state or unfenced panel restore are separate failure classes that still require the panel authority and external fencing. No universal zero-overuse or power-loss guarantee is claimed.

Normal reservation commits are amortized over raw traffic, not performed per byte. The 131,073 one-byte test performs three reservations; local measured unlimited throughput is ~29–34 MB/s with the 64 KiB quantum, much lower than memory-only operation. Larger quanta/group commit need explicit crash-budget tradeoffs and new measurements before acceptance.

Committed cumulative records are now available through protected API v1; see [control-api.md](control-api.md). The panel must still implement transactional cursor/totals settlement before these records become its reliable ledger.

## Stable database identity and panel settlement primitives

`clients.stable_id` is a generated canonical UUID with a unique index and create-only ORM writes. Legacy nullable/empty identities are backfilled transactionally before creating the index. Existing integer primary keys, credentials, email-keyed counters and quotas remain intact. Renames and credential changes cannot overwrite the stable ID through ORM saves. Full SQL backups and SQLite-to-PostgreSQL migration preserve the new tables and IDs; portable client exports and node identity reconciliation still require task 11/12 integration.

The panel explicitly binds a core instance to a node key. Automatic replacement of an existing binding, an older capability epoch and a cursor gap are rejected. A receipt's commit epoch may legitimately precede the current core epoch. `PrepareClientPolicyLedger` stores the old upload/download values and their sum at multiplier 1 as a once-only seed; another source starts with zero seed instead of duplicating that history. This does not allocate a global quota to that source.

Core `InitializeClient` persists policy and usage in one transaction and retains an initialization digest across future policy changes/checkpoints/restarts. Repeating the identical request never rewinds current usage or policy. A conflicting seed, an already-existing unseeded identity or a revoked identity is rejected. Both failures before commit and errors returned after a committed write have recovery tests. An already-exhausted legacy account stays exhausted.

`SettleClientPolicyLedger` uses the shared serialized DB writer and one SQL transaction for source cursor, per-source/client receipt and client cumulative totals. Only committed cumulative differences are added; billed deltas are never multiplied again. Duplicate/older pages do not add usage. Counter/version regression, invalid fractions, unprepared identities, wrong source, future epochs and cursor gaps reject the entire page. All SQL integers are checked against signed 64-bit limits before conversion/addition. Frozen crash uncertainty stays separate from confirmed billed and raw counters; outstanding reservations are receipt metadata, not confirmed traffic. Receipts/totals survive deletion and cannot follow an email to a replacement UUID.

The primitives are exercised through real core/Tunnel/private gRPC connections and SQLite/PostgreSQL databases. Local Runtime now supports seeded process bootstrap, and the existing client-edit service hot-applies changes for clients already present in the running managed configuration. Automatic initial activation still must stop/flush the prior accounting path before preparing its seed, bind the managed listener/account, and switch the UI/statistics consumer without double counting. Existing legacy counters are deliberately not rewritten by settlement before that cutover. Period resets, renewal, portable exports, snapshot restore and cross-node budget allocation remain separate unfinished integration gates.

## Panel policy settings and versions

Client input accepts an optional `policy` object with `uploadBytesPerSecond`, `downloadBytesPerSecond` and a decimal-string `multiplier`. Omission preserves an existing client's settings. Missing initial settings mean unlimited directional rates and multiplier 1; zero rates explicitly remove a limit. Rates must be integers from 0 through 2^40 bytes/s. Multiplier uses the core's exact parser: 0.000001–1000, at most six fractional digits; zero, exponents, NaN and excess precision are rejected. These stored settings do not themselves establish enforcement for a protocol without managed identity activation.

Desired policy compilation locks authoritative client rows and commits a fingerprint plus monotonic `desiredPolicyVersion` in one transaction. Renames and credential changes do not change that version; enforcement changes do. Concurrent identical preparation reuses the committed version, and an invalid batch commits none of its version changes. Ordinary ORM account saves cannot overwrite these reconciliation-owned fields. The version denotes desired configuration, not proof that a core has acknowledged it.

For an already managed local client, the existing edit service prepares that version and dispatches through Runtime to the capability-negotiated private API. Runtime requires an initialized client, applies the bounded atomic batch, and updates the process configuration snapshot after acknowledgement. The core keeps cumulative history and applies new rates/multiplier to existing sessions. Application failures return an explicit error even when the desired edit has been saved. New-client activation, all bulk/lifecycle entry points, first-use expiry and period-reset baselines still require integration; negative first-use expiry is currently rejected by managed policy compilation instead of becoming unlimited.

## Committed-ledger collection

For an already managed local process, the existing `GetXrayTraffic` entrypoint now collects durable client receipts through Runtime before querying legacy operational counters. Runtime validates the stored cursor against the core before checkpointing: a checkpoint must not advance the core past an invalid future cursor and hide a rollback. Each SQL page commits totals, receipts and cursor together. Failures are returned and logged; a subsequent poll resumes from the database cursor, including after a panel restart. The collector never multiplies billed usage again.

Pages contain at most 1000 clients, with at most 101 pages per poll and a ten-second RPC context. Continued churn or a deadline failure leaves committed pages intact for the next poll. The Runtime mutex covers only core RPCs, not SQL settlement. Collection does not hold the process replacement lock across database work; negotiated instance IDs and monotonic epochs reject incompatible or stale replies.

Core checkpointing writes only clients with uncommitted usage or reservations. Policy changes already commit their usage boundary, so an immediately following idle checkpoint does not rewrite that client. An exhausted raw reservation still requires a checkpoint, and fractional billed remainders survive it. This reduces idle writes without changing the reservation/crash bound. Legacy counter projection, quota/reset lifecycle cutover and automatic managed activation remain unfinished.

Managed process activation honors an explicit caller deadline for database preparation and listener activation. Capability negotiation has its own maximum ten-second deadline. If the caller supplies no deadline, activation retains the ten-second default; large configurations require an explicitly bounded activation window. This does not change the two-second target for policy edits on existing flows.

Removing a core inbound now cancels and closes its established TCP, Unix socket and UDP connections and waits for their protocol workers to exit. Once removal returns, the old listener's sessions cannot continue under a new owner's binding. Other listeners sharing the previous client identity remain active and retain their accounting. UDP cleanup checks the connection instance before deleting its tuple, so a finishing old session cannot erase its replacement. This is the core prerequisite for ownership changes; panel ownership assignment and the legacy accounting handoff are still unfinished.

VLESS, VMess, Trojan and classic Shadowsocks AEAD account settings now preserve a server-configured `clientId` through authentication. VLESS/VMess also retain the earlier protobuf spelling `client_id`, rejecting conflicting aliases. Real TCP/UDP/Mux tests share the same policy with Tunnel and count decoded payload once. Capability checks protect managed Handler API mutations, including before the legacy Shadowsocks remove-then-add path. Missing protocol support or a non-private control endpoint produces an error; omitting managed identity preserves the legacy API path. This does not yet make the ordinary panel account compiler automatically supply stable identities.

The managed candidate compiler now resolves local enabled listeners through client_inbounds and ClientRecord.StableID, replacing raw identity fields with database-owned identities. Tunnel requires exactly one owner. Authenticated VLESS/VMess/Trojan/classic AEAD accounts retain their credentials even when restricted; the core policy controls admission. Unknown/manual business listeners, unresolved owners, unimplemented adapters, unverified Vision and clients also attached to remote nodes are rejected explicitly. Only an explicitly configured legacy Tunnel control listener is replaced by private Unix control.

The compiler validates the core candidate before preparing durable policy versions in batches of 1000. Its real-child test seeds historical usage once, runs two generated Tunnel listeners and settles through the existing traffic collector. Candidate generation is separate from production activation: ordinary RestartXray still follows the existing path. Legacy statistics handoff/projection, reset windows, first-use expiry, managed runtime mutations, internal management listeners and configuration revision fencing require further integration.

Quota windows now use `quotaBaselineBytes` plus `quotaBaselineRemainder` (millionths of a billed byte). Enforcement subtracts this baseline from lifetime confirmed billing plus frozen uncertainty, then compares the exact difference to quotaBytes. Zero quota remains unlimited. The baseline cannot exceed current effective usage, even for an unlimited policy; changing it requires a newer policy version. Subtraction avoids overflowing an absolute lifetime-plus-quota ceiling. The lifetime raw directions, billed totals, fraction and uncertainty are never zeroed by this operation.

A policy update commits the exact prior usage and releases unused reservations together with the new baseline. Identical retries keep that boundary. Manual disable, expiry and revocation remain independent. Resetting after a crash can deliberately credit uncertainty belonging to the prior window by including it in the baseline; the uncertainty remains visible in the lifetime ledger. Restart alone never advances the baseline. Legacy zero-baseline initialization digests remain compatible. This is a core/control prerequisite: panel period projection, durable reset requests, renewal and scheduled reset integration are still unfinished.

The panel now stores reset requests separately in `client_policy_resets`, uniquely keyed by stable client ID and caller request ID. Each record captures a committed local receipt's source/epoch/sequence, raw directions, confirmed billed amount and fraction, frozen uncertainty, and resulting desired policy version. The reset record and desired version commit in one SQL transaction; neither lifetime totals nor receipts are cleared. Outstanding reservations are excluded from the credited baseline. The exact window boundary is the captured committed receipt; subsequent admitted traffic belongs to the new window once that policy is applied.

Normal desired-policy preparation loads the latest reset boundary in bounded client batches. Repeating an earlier request returns the current desired policy and never captures newer usage, even when a later reset has already occurred. Disabled and expiry fields remain authoritative client settings. Unsettled or revoked clients, ambiguous/multiple sources, remote attachments without coordinated budgets and inconsistent policy versions are rejected. This is durable preparation: production reset endpoints, Runtime application/retry orchestration, reset scheduling and period statistics still require integration.

`ResetLocalClientPolicy` now pins the active process under restart serialization, checkpoints and settles through Runtime, commits the request, then applies its policy through Runtime. A control failure after SQL commit reports that application is pending; it does not undo the recorded boundary. Normal `GetXrayTraffic` polling compares stored reset versions against committed receipts and the process configuration, retries pending policies in batches of at most 1000, and settles the resulting acknowledgements. An old request never captures traffic admitted after its original boundary. Reset and ordinary preparation with a stored reset recheck remote ownership before application. No Runtime RPC mutex is held during SQL work.

This orchestration requires a running, already managed local core. A stopped core rejects a new reset without adding a request. The single-client entrypoints described below now use this orchestration. Bulk/all-client and scheduled reset integration, automatic production activation and coordinated global budgets remain open.


Existing client statistics now include an optional `accounting` projection for acknowledged local single-source policy receipts. Client lists, paged rows, inbound slim/detail views and client statistics snapshots carry the same projection. Its `lifetime` and `period` fields distinguish upload, download, confirmed billed usage and frozen uncertainty. `period` subtracts the latest reset whose policy version the receipt has acknowledged; preparing a reset alone leaves the old window visible. `resetPending` and applied/desired version strings expose that delay. Unlimited quota returns a null remaining amount. Decimal strings preserve whole bytes and millionth-byte fractions across JSON and JavaScript, including values near signed 64-bit limits.

The client traffic cell, including mobile rows and inbound client details, uses period billed usage plus uncertainty for quota display. Its popover exposes lifetime usage and exact byte values; websocket updates retain accounting-only changes and clear an old projection when the replacement snapshot omits it. Stable IDs join receipts to current client records, so email reuse cannot inherit the prior identity's ledger. Unattached client rename now moves the traffic row transactionally with its record, rolling both back on a statistics write failure.

This is a read projection, not a second accounting authority. Legacy raw fields retain their existing meaning. Legacy quota enforcement, renew/reset writes, page filters/summaries and inbound aggregate badges still require cutover. Only already acknowledged local managed clients without remote attachments receive the projection; multi-source accounting and global allocation remain unfinished. Displayed desired versions describe prepared policies, not yet every offline client edit.

The existing single-client reset service and inbound service entrypoints now identify prepared accounting by stable client ID. A captured bootstrap seed, including a version-zero receipt, protects the identity from legacy counter zeroing even while the core is stopped. An identity still configured in the current managed process is also protected if SQL receipts and totals disappear; reset then returns the ledger inconsistency instead of clearing legacy usage. Legacy reset transactions lock the client row and recheck for prepared accounting before touching counters or group/global/node baselines; initialization takes the same row lock before capturing its seed. The client-facing path also checks the resolved identity again inside the legacy transaction, rejecting an email replacement while the request was queued.

`POST /panel/api/clients/resetTraffic/:email` accepts optional JSON `clientId` and `requestId`. Supplying a request ID requires its stable client ID; mismatched ownership is rejected. Managed requests reuse the existing durable request key, so a retry cannot grant a later period boundary. Empty-body clients retain compatibility but receive a fresh server key per call. The browser stores a managed reset's key in tab session storage before sending it, keeps it after transport failures or `success:false`, and releases it only after success. A rename keeps that key; an email reused by a different identity does not. Polling refreshes the acknowledged view after a pending application.

This connects manual single-client resets for already managed local policies. Bulk/all-client resets, deterministic scheduled keys, renewal, legacy quota/first-use writes, and complete mutation-versus-activation fencing remain open. In particular, this transaction guard covers the legacy zeroing step; later legacy auto-enable/configuration writes still require the activation fence before ordinary startup can switch to managed mode.

## Batched manual resets

`client_traffic_reset_batches` stores the request scope, normalized explicit-selection hash, original stable identities, and SQL completion/result. The first attempt captures membership before requiring a ready core. A retry follows renamed identities, excludes replacements and later additions, and skips deleted identities. The request key cannot be reused for another scope or explicit email selection. An empty selection is also persisted; retrying it cannot reset future clients. Metadata is copied by cross-database migration and included in normal database backups. This does not establish coordinated panel/core snapshot rollback safety.

The existing bulk, all-client and inbound-client service entrypoints use the same operation. Managed clients checkpoint the core once, prepare all reset boundaries in one SQL transaction using batches of at most 1000 identities, then apply policies through Runtime in batches of at most 1000. The selection limit matches the managed store's 100000 identities. No Runtime application occurs on a SQL failure; after a Runtime failure, polling retries committed versions. For a mixed bulk operation, legacy counters, client enable, inbound enable, and remote dirty flags commit together with the managed boundaries. Subsequent Runtime synchronization reads the current desired state under the inbound mutation lock, preserving later manual edits even if another managed apply fails. Retrying the operation does not zero subsequent legacy traffic or clear a later manual disable. Pure managed resets do not request a whole-core restart.

The all-client HTTP endpoint accepts an optional `requestId`; the bulk endpoint accepts it alongside `emails`. Omission generates a fresh key and does not permit safe replay. The browser retains an all-client key across uncertain replies and reloads, scoped to the panel base path. Inbound selection uses authoritative client links, not the stale traffic-row inbound ID. Resetting an inbound's client selects its shared client window, not an independent per-inbound allowance. Calendar deduplication, renewal, legacy auto-enable/activation fencing and ordinary managed startup remain open.


## Scheduled traffic resets

The existing periodic job now captures one durable calendar operation for the configured period and panel time zone. Its original membership combines authoritative inbound links and due client cycles by stable ID; it also captures the due inbound IDs. A repeat in that occurrence cannot add newly created clients or clear subsequent client/inbound usage. Hourly occurrences distinguish the repeated daylight-saving hour; daily/monthly occurrences follow the local date, weekly boundaries start Sunday, and monthly reset days clamp to month end. Calendar metadata is internal and does not interpret user-supplied manual request IDs.

`client_traffic_reset_times` records each stable client's latest effective reset time in the reset transaction. Manual managed, legacy single, and batch resets participate. A delayed calendar task excludes identities with an equally recent or newer accepted boundary; managed imports without this new table can derive the prior manual boundary from reset history. Eligible managed clients retain independent disable and expiry settings. Client-owned legacy cycles recheck the existing depletion/manual-disable distinction before zeroing or enabling. Inbound counters and last-reset dates commit with the selected client changes.

For an already managed process, ordinary traffic polling resumes up to eight pending calendar operations after collecting receipts and reconciling committed policies. Newer unattempted periods run first; persisted attempt times rotate failed tasks so more than eight failures cannot starve older valid work. One failed calendar does not stop independent operations or ordinary traffic collection. A SQL-completed managed reset still uses the existing policy acknowledgement/retry path, without a second window.

Legacy node counter resets retain bounded concurrent Runtime calls after SQL commit. This preserves the existing best-effort legacy node behavior; it does not provide durable remote reset acknowledgements or coordinated global policy budgets. Database migration preserves original selections, calendar ordering and retry state, and accepts older manual-batch schemas without calendar columns. Full panel/core snapshot fencing, renewal, legacy enforcement cutover and ordinary managed startup remain open.

## Managed renewal and legacy lifecycle exclusion

The normal local traffic poll advances due managed clients through committed receipt boundaries. Expiry, renewal count, attached settings and the desired policy version commit together. A renewal that reaches the present opens one quota window; a prepaid cap exhausted in historical catch-up leaves the client expired and preserves its period usage. Neither path changes manual enable or lifetime counters. Settings edits retain exact JSON integer values.

Normal polling now reconciles all committed desired policy versions, including expiry-only updates with no quota-reset row. SQL preparation failures leave the prior state intact; failure after commit is retried without spending another renewal allowance. Prepared/active identities are excluded from legacy raw-quota disabling, automatic enable/zeroing and first-use conversion. Durable managed first-use activation and ordinary managed startup remain unfinished.

## Transactional collection of legacy operational counters

The production traffic job reads non-resetting cumulative Xray statistics. Each
child process owns its cursor and retains a pending batch until SQL acknowledges
settlement. Inbound, client and outbound deltas, first-use expiry changes and a
`legacy_traffic_receipts` row commit in one transaction. Failure rolls them back
without advancing the cursor. If SQL committed but its acknowledgement was lost,
retrying the same process ID, sequence and batch ID recognizes that commit and
does not add the deltas again. Traffic arriving during that retry is collected
in the next batch. The first poll includes traffic already observed by the child.

There is one latest receipt per child, preserved by database migration/export.
The process guard serializes polls with child shutdown, and a new child gets a
new cursor and identity. Inbound and outbound statistics with the same tag stay
separate. Zero-byte reports do not activate a delayed-start client's expiry.
Lifecycle and remote notification work retains its existing best-effort behavior.

These operational counters continue to update for managed clients. Managed
billing and quota use the independent durable policy ledger; legacy raw fields
are neither frozen migration seeds nor an additional billing authority. The
initialization seed is retained in the policy receipt. This collector cannot
recover legacy bytes that were never observed before a core crash. A verified
final accounting drain and automatic legacy-to-managed handoff remain open.
