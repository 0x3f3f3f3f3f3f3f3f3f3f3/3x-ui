三、不可偏离的单内核架构

部署形态：

每个节点：
- 一个 3x-ui 面板或节点管理进程。
- 一个 Custom Xray-core 业务数据面进程。

面板可以是独立进程；“单内核”指业务代理、隧道和转发流量由同一个 Custom Xray-core 承载。

目标结构：

3x-ui 控制面
├── Web UI / REST API
├── 用户、凭据与服务配置
├── 数据库与计费账本
├── 订阅、分享与配置导出
├── 节点、版本、部署和健康管理
└── Core Adapter / gRPC 控制接口
                  │
                  ▼
单一 Custom Xray-core
├── 入站协议适配
│   ├── 原有 Xray 协议
│   ├── Snell v4 / v5 / v6
│   ├── mieru
│   ├── SSH Tunnel
│   └── 任意门 / Tunnel 端口转发
├── 统一 Client Identity
├── 统一 Client Policy Engine
│   ├── 上传/下载聚合限速
│   ├── 原始流量计量
│   ├── 计费倍率与额度执行
│   ├── 到期、禁用和限制原因
│   └── 活跃连接与 UDP 会话登记
├── Xray Dispatcher / Router / DNS / Balancer
├── 原有及新增的出站适配
└── 统计、策略、用户和连接控制 API

注意：以上是逻辑职责，不强制要求所有代码按这个文件名组织。
实际执行顺序应依据协议和 Xray 的源码结构设计，但每条业务数据路径都必须经过统一身份与策略检查。

明确禁止：

1. 同时运行 Xray + sing-box。
2. 同时运行 Xray + Mihomo。
3. 外置 snell-server、mita、业务用 sshd 等进程来实现新增协议。
4. 把 Snell/mieru/SSH 解码放到面板进程，再经本地 SOCKS/HTTP 端口转接到 Xray。
5. 将两个完整内核静态打包进同一二进制，却各自保留独立的路由、用户和统计体系。
6. 每个用户启动一个独立核心进程。
7. 使用 shell 脚本代理真实数据路径。
8. 为了满足“单进程”的表面要求，隐藏第二套独立代理系统。

允许：

- 将成熟、合规的协议库作为编译期依赖。
- 移植必要的协议实现并适配 Xray 的连接、数据报和上下文接口。
- 在同一核心中运行多个 listener、协议实例和 goroutine。
- 为 SSH 使用成熟的 Go SSH 库。
- 复用协议库内部必要的握手、加密和传输逻辑。

使用协议库时必须控制其真正的目标连接入口：
不能让库绕过 Xray Router 和 Client Policy Engine 自行连接目标。

宿主机已有的管理 SSH 不属于本项目业务数据面，必须保持原样，不能停用或篡改。

如果当前面板已有由独立进程或面板本身承载的业务协议：
- 先审计实际存在的功能，不依据架构示意图猜测。
- 将其纳入单内核迁移计划。
- 保留其实际功能和用户数据。
- 未完成迁移时应明确记录，不能把最终系统宣称为“全部单内核”。

五、统一客户端身份与运行时策略

实现内核级稳定 client_id。

1. client_id 来自面板管理系统，不随昵称、展示 email、凭据轮换或端口变化而改变。
2. 为旧客户端建立兼容映射，不能破坏现有统计和 API。
3. 审计 Xray 当前版本的用户、session、上下文和统计结构，在合适位置扩展。
4. 不把新增字段假装成上游已经支持的原生配置。

身份来源：

- UUID/密码型协议：认证后的账号映射到 client_id。
- Snell：已验证的 PSK/协议账号或独占 listener 映射到 client_id。
- mieru：认证后的用户映射到 client_id。
- SSH：认证后的账号和公钥/密码映射到 client_id。
- 端口转发：已配置的监听资源归属映射到 client_id。

不能直接信任客户端提交的任意 client_id、email 或 username 字符串；必须以完成认证或服务端可信资源绑定后的身份为准。

同一 client_id 可以关联：
- 多个协议账号。
- 多个入站。
- 多个端口转发规则。
- 多个并发连接。
- 多个复用 channel。
- 多个 UDP 会话。

默认按同一 client_id 汇总管理，不能通过新增连接、规则或凭据获得额外限速和额度。

在实际数据路径中保留：
client_id、inbound_tag、认证身份、原始目标、实际目标、传输方向、策略版本、会话/连接标识及必要计量上下文。

不能仅在日志中保留这些信息，而让运行时执行路径无法使用。

实现统一 Client Policy Engine，至少包含：

- 上传和下载共享限速器。
- 原始流量计量。
- 倍率、额度和剩余可用预算。
- 到期和人工禁用状态。
- 活跃连接及 UDP 会话登记。
- 按 client_id 关闭连接。
- 策略版本与热更新。
- 并发安全和资源释放。

核心策略状态必须作用于已有连接，不得只在建立连接时读取一次。

审计所有绕过常规复制路径的实现：
包括复用、快速转发、零拷贝、Vision/XTLS 或选定版本中的其他特殊路径。

启用了限速或额度的用户，不能通过这些路径绕过执行。
必要时仅对受管连接切换到可执行策略的路径，并提供性能对照；不要无依据地全局禁用优化。


六、在 Custom Xray-core 中实现 Snell v4/v5/v6

1. 将三个版本作为独立兼容目标。
2. 联网查阅官方客户端要求、服务端说明、版本差异及可靠实现。
3. 优先复用可合法嵌入的成熟协议实现，适配到 Xray 内部。
4. 不自行设计一个名称叫 Snell、但只能与自制客户端通信的私有协议。
5. 不允许依赖独立 snell-server 进程。

必须分别处理和验证：
- 握手和认证。
- TCP 数据流。
- UDP 转发。
- 连接复用和会话生命周期。
- 各版本实际存在的特殊传输能力。
- 目标地址、域名和 client_id 的传递。
- 路由、计量、限速和超额断流。

特别要求：

1. 不因为 v4/v5 部分行为相近，就将它们作为同一配置选项且只测试一个。
2. 核对 v5 的 QUIC Proxy 等版本专属能力；不能以普通 TCP/UDP 连通替代其验收。
3. v6 如果执行时仍为 beta，固定明确的客户端/实现兼容组合并标注。
4. 不能因为配置中允许填写 version=6，就宣称已经兼容 v6。
5. 真实客户端互操作和自制测试客户端互测必须分别记录。

多用户：

- 能够可靠区分认证身份时，支持同 listener 的独立用户。
- 如果协议或所用实现不支持可靠的多 PSK 用户识别，应使用同一核心内的独立 listener/端口等方案。
- 不能通过运行多个内核来隔离用户。
- 不能让多个 client 共用无法区分的认证身份和计数器，却声称独立限速和扣量。
- 避免无限遍历大量密钥造成认证阶段 CPU 或拒绝服务风险，明确资源限制。

为 Snell 提供入站适配及所需的出站适配，使其能参与统一的出口选择和代理链。
入站支持与出站支持必须分别验证。

如果某版本缺少可用、合规的嵌入实现：
继续开展协议兼容实现或适配工作，并记录证据与缺口。
不得静默回退到外部服务，也不得把其他版本冒充该版本。


七、在 Custom Xray-core 中实现 mieru

1. 优先评估官方提供的可嵌入 API/协议库和对应版本源码。
2. 在同一 Xray 进程内完成服务端接入，不运行独立 mita 进程。
3. 复用认证、传输和加密实现，但将认证身份、目标请求和实际数据流接入 Xray。
4. 若库提供 Accept、连接上下文或目标请求接口，优先利用。
5. 如果库默认自行处理目标连接，应通过受控接口或源码适配接入 Dispatcher；不能允许其独立直连绕过路由。

必须实现：

- 用户名/密码与 client_id 的稳定映射。
- 用户创建、删除、禁用及凭据变更。
- 适用的 TCP/UDP 能力。
- 多连接、复用和会话管理。
- Xray 路由及出站选择。
- 聚合限速、原始统计、倍率和额度。
- 到期及对已有连接的终止。
- 与面板统一的配置、API、日志和导出。
- 对应出站适配及真实互操作测试。

如果协议库自身提供统计或配额：
应明确哪些数据作为底层观测，哪些由统一策略引擎执行。
不能让两套配额窗口和扣量逻辑同时独立生效，造成重复扣费或行为冲突。

特别测试：
停止 listener、删除用户或修改配置后，已有连接是否仍在运行。
不能把“停止接受新连接”当作“已终止该用户全部流量”。


八、在 Custom Xray-core 中实现 SSH Tunnel

本需求包括：
A. 用户通过 SSH 连接本机使用隧道。
B. 将 SSH 作为可供统一路由选择的上游出站。

二者分别建模和验收，不能只实现 SSH outbound 就宣称支持 SSH Tunnel 服务端。

服务端实现：

1. 使用成熟 SSH 库，在 Custom Xray-core 内新增受管理的 SSH 入站。
2. 不调用外部 sshd，不创建业务 Linux 系统账号，不修改宿主机管理 SSH。
3. 支持标准 SSH 客户端可用的：
   - 本地转发 -L。
   - 动态转发 -D。
   - 远程转发 -R，默认关闭，仅经管理员显式授权后启用。
4. 正确处理相关 channel/global request，而不只是建立加密连接。
5. 对 -L/-D 的目标连接接入 Xray Dispatcher。
6. 对 -R 建立同一核心内受管理的反向 channel 数据路径，纳入身份、额度、限速和连接登记。
7. -R 场景中客户端决定、且服务端不可见的最终目标信息，不得伪装成服务端已掌握的域名路由条件。

安全要求：

- 公钥认证优先；密码认证按明确配置启用。
- 每个 client 具有独立认证身份。
- host key 由业务服务单独管理和持久化。
- 不复用本任务 GitHub 凭据。
- 默认拒绝 shell、exec、PTY、SFTP、SCP、agent forwarding、X11 forwarding 和无关 subsystem。
- 远程转发监听地址、端口范围、来源范围和资源数量必须受控。
- 对认证尝试、握手时间、连接数、channel 数、缓冲区和空闲会话设置合理上限。

聚合执行：

- 同一用户多个 SSH 连接以及同连接多个 channel 共享限速和额度。
- 禁用用户时关闭已有 channel 和相关连接。
- 撤销远程转发时释放对应 listener。
- 明确反向转发中的上传/下载方向。
- 不把标准 TCP 隧道支持宣称为任意 UDP 隧道支持。

SSH 出站：

- 在同一内核内完成 SSH 上游连接。
- 严格验证主机密钥。
- 凭据与入站账号分离。
- 接入统一路由、日志和连接管理。
- 对连接池和复用进行用户上下文隔离，不能混淆计量归属。


九、优先使用 Xray 任意门实现端口转发

这是本次明确的首选实现，不再默认使用 iptables/nftables 做业务转发。

请首先审计选定 Xray 版本的：
dokodemo-door / Tunnel 实现、配置解析、Dispatcher 接入、TCP/UDP 转发和统计路径。

按实际版本确认：
- 协议注册名称及旧名称兼容。
- network / allowedNetwork 等字段。
- address / port 与 rewriteAddress / rewritePort 等字段。
- portMap 或其他端口映射能力。
- followRedirect 和透明代理相关配置。

以上字段是核对项，不是要求同时写入同一份配置。
不得机械混用不同版本的 JSON schema。

默认数据路径：

外部 TCP/UDP 连接
→ Xray 任意门 / Tunnel listener
→ 根据可信转发规则绑定 client_id
→ 统一 Client Policy Engine
→ Xray Dispatcher / Router
→ 选定 outbound
→ 目标服务

必须先完成最小可运行的数据面验证：
- TCP 固定目标端口转发。
- UDP 固定目标端口转发。
- 经直接出站转发。
- 经指定代理出站转发。
- client_id 进入统计和策略执行路径。

再扩展为面板完整功能。

端口转发配置至少包含：

- 规则名称与备注。
- 所属节点。
- 所属 client_id。
- 监听地址、监听端口。
- TCP、UDP 或 TCP+UDP。
- 目标地址和目标端口。
- 指定出站或参与路由的方式。
- 来源访问控制。
- 启用状态。
- 用户级限速、倍率、额度和到期信息。

用户归属：

1. 普通端口转发没有业务账号认证，因此必须绑定服务端管理的监听资源归属。
2. 默认一个“节点 + 传输协议 + 监听地址 + 监听端口”资源只归属一个 client。
3. 同一 client 可以拥有多个转发规则，并与其其他协议共用策略。
4. 不使用源 IP 作为唯一 client 身份。
5. 不允许无法区分归属的共享监听资源伪装成多用户独立服务。
6. 明确告知：能访问某用户专属监听资源的流量，会消耗该资源所属用户的额度；来源 ACL 负责进一步限制访问。
7. 处理通配监听、IPv4/IPv6 双栈、端口复用和现有管理端口的冲突。
8. 删除、重建、重新分配端口时，旧连接和旧计量不能归入新用户。

内核扩展：

- 如果原生任意门无法附加完整用户身份，在其可信入站上下文中补齐。
- 可复用现有用户结构，但应增加稳定 client_id 映射。
- 不把 userLevel 当成唯一用户身份。
- 不能只用 inboundTag 统计而不进入用户级限制。
- 不要仅修改 UI 给任意门增加一个 client 字段，实际数据路径却完全忽略它。

转发语义：

- 默认实现显式监听的用户态 L4 端口转发。
- 不默认开启透明劫持、TPROXY 或系统级流量重定向。
- 普通端口转发不应要求修改全局 NAT 规则或开启全局 IP forwarding。
- 不把用户态转发描述成透明 NAT，也不声称它天然保留客户端源地址。
- 处理 TCP 半关闭、长连接、UDP 会话超时、双向流量和目标不可达。
- 支持目标域名时，明确 DNS 解析、刷新、地址变更和现有连接策略。
- IPv4/IPv6 支持与跨地址族转发必须分开验证。
- 任意二进制流量只能使用实际可获得的路由信息，不能保证必然存在可嗅探域名。
- 出站协议不支持某种网络类型时明确报错，不能静默改为直连。

额度和禁用：

必须作用于已有的转发 TCP 连接和 UDP 会话。
不能仅删除 listener、拒绝新连接，或修改数据库 enable 字段。

如果现有任意门接口不足，优先扩展同一 Xray-core。
没有证据证明该方案存在阻塞之前，不要改换另一个转发后端。
即使遇到阻塞，也不得未经说明回到多内核或外部转发进程架构。


十、内核级 per-client 上传/下载限速

限速覆盖现有和新增的适用协议，包括任意门端口转发。

默认语义：

- 以 client 视角定义上传和下载。
- 上传、下载分别配置。
- UI 清晰区分 Mbps、MB/s，内部采用明确单位。
- 0 表示该方向不限速。
- 拒绝负数、溢出和无效值。
- 旧用户迁移后默认不限速。
- 一个 client 的全部连接、channel、UDP 会话和转发规则共享该方向限速。

实现要求：

1. 在 Custom Xray-core 的统一流/数据报路径执行限速。
2. 优先使用共享 token bucket 或等效可验证机制。
3. 不是每条连接各自获得一份完整限速。
4. 不按源 IP、共享端口或整个核心进程代替用户限速。
5. 不能依赖外部 tc/nftables 才使本任务的基础用户限速成立。
6. 不能用调整 bufferSize、连接数或简单周期性断流冒充限速。
7. 队列和 burst 必须有界。
8. UDP 保持数据报完整性，并明确拥塞时的排队/丢弃策略。
9. 防止一个连接长期占满同一用户的全部调度资源。
10. 策略更新要作用于已有连接，默认验收目标为 2 秒内生效。
11. 倍率变化不得改变原始带宽上限。
12. TCP/UDP、复用和快速路径都不能绕过限制。

提供理论上限和实际测试：
对于限速 R、允许 burst B 和观察窗口 T，说明累计可通过字节的上界及计时/缓冲误差来源。

不能只证明吞吐低于上限：
在健康、低竞争且基线吞吐充足的环境中，也要证明实现不会把连接长期压到远低于配置速率。


十一、流量计费倍率、额度与持久化

每个 client 配置独立倍率：

- 默认 1。
- 支持正数小数，例如 0.5、1、1.5、2、10。
- 明确范围、精度及非法输入处理。
- 本次不默认引入倍率为 0 的免费模式。

默认计费规则：

新增计费流量
=（新增原始上传流量 + 新增原始下载流量）× 生效倍率

例如：
额度 100 GiB，倍率 2，没有历史用量且倍率不变时，
可使用约 50 GiB 的原始上传与下载合计流量。

必须分别保存、展示：
- 原始上传。
- 原始下载。
- 累计计费流量。
- 配额。
- 剩余额度。
- 当前倍率。
- 生效策略版本和必要结算信息。

计量边界：

1. 对能提供统一接口的协议，以解封装后的 TCP 字节流/UDP 数据报负载等明确业务边界计量。
2. 避免将内部桥接、重复读取、嗅探缓冲、协议加密填充和底层重传重复计入。
3. 对 IP 包型协议或不能完全等价的路径，明确其计量口径及显示方式。
4. 不允许不同口径在同一界面中无说明混用。
5. 管理 API、健康检查和核心内部控制流量不能计入普通 client。
6. 同一业务流在入站、出站和代理链内部不得被重复扣量。

倍率计算：

- 使用定点数、整数比例或等效精确机制。
- 保留不足一个最小计费单位的余量。
- 相同流量拆成不同上报批次，最终计费结果必须一致。
- 防止溢出、逐批舍入误差和浮点累计误差。
- 不允许在前端乘倍率、后端却继续按原始流量判断额度。

倍率热更新：

已使用 10 GiB、倍率 1；
改为 2 后再使用 5 GiB；
累计计费应为 20 GiB。

历史已计费流量不追溯重算。
切换必须有明确策略版本和计量边界，不能把切换前后全部未结算流量套用同一个倍率。

额度执行：

1. 在核心数据路径中扣减预算、检查额度。
2. 不依赖面板每隔若干秒轮询后才进行封禁。
3. 同一用户多个连接并发竞争剩余额度时，需要原子预算控制。
4. 流量耗尽后拒绝新连接，并关闭或阻断已有 TCP/channel/UDP 流。
5. 降低额度到已用量以下时立即进入受限状态。
6. 重启面板、核心或服务器后，不得重新获得已消耗的额度。
7. 重置、续期和增加额度只解除对应限制原因，不得覆盖人工禁用或其他仍生效的限制。

持久化：

- 3x-ui 保存配置和长期账本。
- 核心保存执行所需状态及可恢复的计量/预算信息。
- 明确唯一配置权威、账本归属和同步协议，不能产生两套独立控制面。
- 处理核心重启、计数器重置、重复/乱序上报、数据库事务失败、异常退出及 client 删除重建。
- 使用核心实例标识、epoch、序列号、策略版本等必要信息建立幂等入账。
- 计量游标、原始累计值和计费累计值必须具有一致的提交语义。
- 不要把可随时清零的内存统计计数器直接当作可靠账本。
- 备份恢复及快照回滚需要考虑旧事件重放和额度重复发放。

可以使用持久化预算预留、有限租约、WAL 或其他合理机制。
必须说明其正常误差、崩溃误差和最大超用量边界，避免逐字节同步写盘导致不可接受的开销。

禁止无证据宣称“绝对零超用”。
应通过架构约束和测试给出明确上界，不能在测试失败后随意放宽标准。

旧数据迁移：
默认倍率为 1，保留已有用量，不清零、不重复扣费。


十二、统一路由、出站和多节点语义

路由：

1. 所有新协议及端口转发进入同一 Xray Dispatcher/Router。
2. 尽量复用现有规则模型和编辑界面。
3. 支持基于实际可获得信息的用户、入站、目标地址、域名、端口和网络类型等条件。
4. 复用现有 DNS、出站、阻断和负载均衡能力。
5. 新增协议的出站适配与入站适配分别验收。
6. 规则中的 client_id 必须来自可信身份上下文。
7. 保留原始目标与改写目标，明确哪一种参与规则匹配。
8. 不允许协议库自行直连绕过路由。
9. 不允许路由失败后静默直连。
10. 检测本机监听回环和代理链循环。
11. 域名嗅探属于有条件能力，不得伪造加密流量中不可得的信息。

多节点：

- 每个节点仍然只有一个 Custom Xray-core 业务数据面。
- 明确用户策略是全局作用域还是节点作用域。
- 对全局 client，不得让 N 个节点各自获得完整额度或完整限速，最后却宣称是一个全局上限。
- 全局额度可采用受控预算分配、租约等机制。
- 全局限速需要总预算协调或有界分配，明确一致性和利用率权衡。
- 面板不可达时，只能按明确的有效策略和剩余预算继续运行，不能自动解除限制。
- 节点上报和主面板汇总不能重复乘倍率。
- 单节点与多节点都必须有可验证的故障恢复语义。

没有完成全局执行能力时，应明确标注范围，不能用节点级实现冒充全局实现。


十三、控制 API、前后端和数据库整合

内核控制 API：

优先扩展与现有面板兼容的控制方式，保留现有必要接口。

至少支持：
- 能力与版本查询。
- 入站/出站和用户生命周期。
- client 身份关联。
- 策略读取与更新。
- 原始计数及计费事件读取。
- 按 client_id 查询和终止连接。
- 到期、禁用和额度状态。
- 配置校验及应用状态。

要求：

1. 不假设原生 AddUser/RemoveUser 已支持所有新增协议。
2. 不破坏已有 protobuf 字段编号、服务名称或客户端兼容性。
3. 新增 API 有明确版本和能力协商。
4. 面板连接到缺少本任务能力的官方核心或旧核心时，应明确拒绝不受支持的操作。
5. 不静默忽略 client_id、限速或倍率字段。
6. 本地接口采用受保护的本机访问方式；跨节点控制使用适当认证和加密。
7. 控制接口不能无认证暴露公网。
8. 日志和 API 响应对凭据进行必要保护。

前后端：

所有新增功能贯穿：
数据库 → 服务层 → API → 前端 → 配置生成 → 核心执行 → 统计展示 → 备份恢复。

必须整合：
- 创建和编辑表单。
- 服务和客户端列表。
- 批量操作。
- 状态和错误提示。
- 在线连接、统计与限制原因。
- 订阅/分享/导出。
- 节点同步。
- 相关通知流程。

使用现有组件、权限校验、样式和国际化规范。
至少完成中文和英文新增文案，其余语言遵循现有回退机制。

不要新建一个与原有用户管理脱节的独立页面。

数据库：
依据实际项目支持的数据库后端设计迁移，不从架构图猜测数据库类型。
新增字段和关联资源必须进入迁移、导入导出、备份恢复和批量操作。

协议配置导出：
严格匹配真实客户端格式。
不支持的客户端不能获得伪造的“兼容节点”。
SSH 和端口转发可以提供适合自身的连接说明或配置，不强行包装成不存在的订阅协议。


十四、构建、安装、升级与运行安全

1. 同时构建面板和 Custom Xray-core。
2. 从干净 clone 能复现构建，不依赖开发机缓存和手工修改。
3. CI 构建使用同样的内核源码、依赖和 build tags。
4. 发布产物记录面板与核心兼容关系、版本和校验值。
5. 安装脚本、Docker 镜像和自动更新必须安装正确的自定义核心。
6. 不得在“更新核心”时无提示换回官方 Xray，使新增协议和策略失效。
7. 保留面板原有适用平台和架构支持；能力缺失时准确门控。
8. 不能为了新增功能让无关原有配置无法构建或运行。

配置应用：

- 先校验后应用。
- 明确热更新和必须重建 listener 的边界。
- 策略、身份、计量和连接生命周期保持一致。
- 失败时保留或恢复已知有效状态。
- 避免因一个用户变更重启整个核心并断开全部用户。
- 大规模配置更新应有资源上限和性能测试。

系统安全：

- 不修改宿主机管理 SSH。
- 不清空全局防火墙。
- 不重置全局 qdisc。
- 不停止 Docker、UFW、firewalld、Fail2ban 或无关服务。
- 不无授权重启主机。
- 网络测试放在隔离环境中。
- 保留原有必要的网络权限，新增权限遵循最小化原则。
- 不把“单内核”理解为“必须以最高权限运行所有组件”。

给出升级、备份、故障恢复和回滚步骤。
数据库降级不安全时，明确使用升级前备份恢复，不能承诺无损直接降级。


十五、测试与验收

在关键实现前确定验收语义、测试方法和容差。
关键问题应先写失败测试，再实现修复。

至少完成以下层次：

A. 单元和性质测试

- client 身份映射与凭据轮换。
- 多连接共享限速器。
- 倍率 0.5、1、1.5、2、10。
- 上传、下载和双向合计。
- 不同批次划分的计费一致性。
- 倍率切换边界。
- 定点余量、溢出和非法输入。
- 额度并发预留与扣减。
- 重复、乱序、重放事件。
- 多种禁用原因组合。
- 旧数据迁移。
- 端口归属、冲突、删除和重新分配。
- API 版本兼容及能力缺失。

B. 协议端到端测试

- Snell v4、v5、v6 分别与真实目标客户端验证。
- mieru 与官方客户端验证。
- SSH 使用标准客户端验证 -L、-D 和受控 -R。
- 新增出站分别验证。
- 原有协议进行回归。
- TCP、UDP、连接复用和长连接按适用范围测试。
- 不以同一份自制实现的服务端/客户端互通作为唯一兼容证据。
- 验证测试流量确实经过待测协议，没有走系统直连或其他代理。

C. 任意门端口转发专项

- TCP 固定地址/端口转发。
- UDP 固定地址/端口转发。
- TCP+UDP。
- IPv4、IPv6 和适用的跨地址族路径。
- 域名目标及解析失败。
- 直接出站、指定代理出站和阻断规则。
- 长连接、半关闭、超时及目标不可达。
- 同一用户多个转发规则聚合执行策略。
- 同一用户“代理协议 + 端口转发”共享限速和额度。
- 用户禁用、超额后已有连接和 UDP 流终止。
- 删除、重建 listener 后无旧流量串账。
- 不依赖临时添加的 NAT 规则才使测试通过。

D. 限速端到端测试

- 单连接和多连接。
- 上传、下载及同时双向传输。
- 多用户同时运行。
- 两个用户共用同一公网 IP。
- 同一用户多入站、多规则和多协议。
- 至少两个非零限速档位及不限速对照。
- 传输期间修改限速，验证已有连接生效时间。
- 测试环境基线吞吐显著高于最大测试限速。
- 使用足够长的测量窗口，分开报告启动 burst 与稳态吞吐。
- 按预先定义的 R、B、T 和误差上界验收。
- 验证正常环境下不会以严重低吞吐或频繁断流“实现限速”。
- 按适用范围验证多节点聚合。

E. 倍率和额度端到端测试

示例：
额度 100 MiB，倍率 2；
原始上传与下载合计约 50 MiB 时应触发限制。

要求：
- 用独立观测在相同计量边界核对用量。
- 区分上传、下载和双向回显，不能忽略回显导致的双向计费。
- 测试倍率切换后历史不重算。
- 测试多连接同时争用最后剩余额度。
- 测试已有 TCP 连接和持续 UDP 流停止。
- 测试重连失败。
- 测试面板重启、核心崩溃/重启后的额度状态。
- 测试重复上报和恢复重放不会重复扣量。
- 报告封禁延迟、真实超用字节和与设计上界的差异。

F. 路由和安全测试

- 用可观察的不同出口验证规则命中。
- 验证按用户、入站、域名/IP、端口及网络类型的适用规则。
- 验证阻断后不能回退直连。
- 验证 SSH 不提供未授权 shell/exec/subsystem。
- 验证反向转发授权和监听范围。
- 验证来源 ACL。
- 验证错误凭据、撤销凭据和非法配置。
- 验证计量、限速和配额不能被复用、快速路径或直接拨号绕过。

G. 故障和性能测试

- 面板失联。
- 核心异常退出。
- 数据库写入失败。
- 配置应用失败。
- 端口冲突。
- 策略热更新并发。
- 用户删除与活跃流量并发。
- 连接、goroutine、文件描述符和内存泄漏。
- 认证阶段及数据报解析的适用 fuzz 测试。
- 与固定版本上游核心进行可比较的 CPU、内存、吞吐和延迟测试。
- 不预设单内核必然更快，报告真实结果。

H. 构建检查

按仓库实际工具链运行：
- 后端测试。
- 适用的 race 检查。
- 静态检查。
- 前端测试及构建。
- 自定义核心构建。
- Docker/安装产物验证。
- 干净环境重建。

每个测试记录：
环境、版本、命令、输入、预期、实测值和是否通过。

缺少商业客户端、指定平台、权限或内核条件时：
提供可复现脚本/步骤，并标记未执行。
mock 测试不能替代真实互操作测试。
skip 不能计入通过。
不得修改测试预期来迁就错误实现。


十六、执行顺序、文档和最终交付

建议按以下依赖顺序执行：

阶段 1：
仓库与版本审计、功能矩阵、内核源码纳管、架构设计、关键风险验证。

阶段 2：
优先用任意门端口转发完成一条纵向闭环：
client_id → 数据面计量 → 聚合限速 → 倍率 → 额度 → 断流 → API → UI。

阶段 3：
将统一身份和策略引擎接入原有适用协议，完成回归。
不能等新增协议全部写完后，才发现统一层无法执行限制。

阶段 4：
在同一核心中逐个整合 Snell v4/v5/v6、mieru 和 SSH。
每个协议一起完成后端、前端、API、路由和真实测试。

阶段 5：
完成新增出站、订阅/导出、多节点、备份恢复和安装升级。
完成审计发现的其他业务数据面迁移。

阶段 6：
全量回归、安全与故障测试、性能测试、文档整理、最终提交和 push 核实。

顺序可以根据真实依赖适当调整，但应解释原因。
不要长期停留在只有接口定义、空适配器和 UI 下拉框的状态。

在仓库中维护：

- implementation-plan：任务分解和当前状态。
- architecture：单核心架构及真实数据路径。
- capability-matrix：协议与功能覆盖。
- accounting：身份、计量、倍率、额度和限速语义。
- testing：测试命令、环境、结果和未验证项。
- deployment：构建、安装、升级及回滚。
- upstream：上游基线、补丁和依赖来源。

文件路径遵循仓库规范，不要求机械采用上述名称。

最终回复必须包含：

1. 面板、内核和依赖的确切版本及 commit。
2. 是否真正满足每节点单一业务内核，并给出进程/部署证据。
3. 任意门端口转发的最终实现、必要内核改动和实测结果。
4. Snell v4/v5/v6、mieru、SSH 的入站/出站支持状态。
5. client_id 如何进入数据路径。
6. 限速、计量、倍率和额度分别在哪里执行。
7. 已有连接如何被关闭，重启后如何保持额度状态。
8. 完整功能矩阵中的未实现、未验证和不适用项。
9. 实际测试命令、结果、误差和跳过原因。
10. 关键 commits、远端分支和 push 核实结果。
11. 从干净环境构建、安装和升级的方法。
12. 回滚方式及剩余风险。

验收底线：

- 不能只改面板而不改内核。
- 不能只有配置字段而没有执行逻辑。
- 不能把其他进程伪装成内核模块。
- 不能把每连接限速冒充每用户聚合限速。
- 不能只修改显示倍率。
- 不能只阻止新连接而保留超额旧流量。
- 不能把任意门转发成功当成用户管理全部完成。
- 不能把多个独立内核包装进一个二进制后宣称统一数据面。
- 不能在缺少验证时声称所有协议完全兼容。
- 不能在存在核心缺口时用“基本完成”代替逐项交付结果。
